Security

Private because of how it is built

Most meeting apps ask you to trust their servers. BinaryBond is designed so the server never has what it would need to listen in.

The key stays in the link

When you start a meeting, your browser generates 128 random bits and places them after the # in the meeting link. Browsers never include that part of an address in requests, so the key is never transmitted to us.

From that key each browser derives three things: a public meeting ID, a membership token and an encryption key. The server learns the ID and keeps only a hash of the token. The encryption key never leaves the device.

What the server can and cannot see

This is the complete list. There are no analytics, no third-party scripts and no logs of who met whom.

InformationVisible to BinaryBond
An opaque meeting IDYes, to route connections
Number of people connected, and whenYes, as aggregate counts
Your IP addressYes, while connected, kept in memory only
Names, chat messages, polls, whiteboardNo, encrypted end to end
Audio, video, screen shares and filesNo, sent directly between devices
The meeting key or linkNo, it never leaves your browser
Connection details (SDP, network candidates)No, sealed with AES-256-GCM

Security features, built in

Each protection works by default. There is nothing to switch on.

Sealed signaling

Handshake messages are encrypted with AES-256-GCM and bound to their sender and recipient, so the server cannot read, forge or redirect them.

Safety numbers

Each pair of participants can compare a 20-digit number derived from both connection certificates. A match proves no one is in between.

Relay mode

Route media through a TURN relay so other participants cannot see your IP. The relay only ever handles encrypted packets.

Clean file transfers

Files are sent directly, hashed with SHA-256 for integrity, and photos lose their GPS and camera metadata first.

Access control

Waiting rooms, locks and removals are enforced by the server, so a leaked link alone is not enough to get in.

Hardened web app

Strict Content Security Policy, no third-party code, rate limits on every endpoint and no cookies.

Limits worth knowing

No system is perfect. These are the trade-offs we have made, stated plainly.

  • Anyone who has the meeting link can ask to join. Use the waiting room for sensitive meetings and share links privately.
  • In direct calls, other participants can see your IP address. Relay mode prevents this.
  • The server knows that a meeting took place and how many people joined. It cannot know who they were.
  • Large group calls are limited to 8 people because every participant connects to every other.
