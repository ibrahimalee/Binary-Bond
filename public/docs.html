Build private calls into your product

BinaryBond gives you end-to-end encrypted video, voice, chat and file sharing with one script tag. Your users' media and messages flow directly between their devices; neither you nor the BinaryBond server can read them.

Quickstart

  1. Get an API key from the dashboard (or from your server operator).
  2. On your backend, mint a short-lived session token.
  3. In the browser, mount the call with that token.
# 1. backend: create a session token (keep your API key server-side)
curl -X POST https://YOUR_HOST/v1/sessions \
  -H "Authorization: Bearer $BINARYBOND_KEY" \
  -H "Content-Type: application/json" \
  -d '{"maxPeers": 4, "ttlSec": 900, "maxMinutes": 60}'

# → { "token": "v1.eyJ0aWQ…", "expiresAt": 1760000000000, "embedUrl": "https://YOUR_HOST/embed?token=…" }
<!-- 2. frontend -->
<div id="call" style="height: 640px"></div>
<script src="https://YOUR_HOST/sdk.js"></script>
<script>
  const call = BinaryBond.mount('#call', { token: SESSION_TOKEN });
  // Share call.inviteUrl (or call.room) with the other participants
  // through your own app. The key never touches any server.
  call.on('joined', e => console.log('participants', e.participants));
</script>

Add your site's origin under Allowed embed origins in the dashboard, otherwise browsers will refuse to frame the call (CSP frame-ancestors).

Session tokens

A session token authorises creating a room under your workspace: it applies your plan limits, counts usage against your quota and enables your branding. People joining an existing room only need the room key, not a token.

FieldTypeDescription
ttlSecintToken lifetime, 30 s – 24 h. Default 900.
maxPeersintRoom capacity, 2 – your plan's maximum.
maxMinutesintRoom time limit, capped by your plan.
relayboolForce TURN relaying so participants never see each other's IP (plan + server support required).
refstringYour own identifier (1–64 of A-Z a-z 0-9 _ . : / -), echoed as data.ref in every webhook and in /v1/rooms.

Embed SDK

BinaryBond.mount(target, options) inserts a sandboxed iframe and returns a controller.

OptionDescription
tokenSession token from /v1/sessions.
roomExisting room key to join. Omit to generate a fresh one (read it from call.room).
height, radius, titlePresentation options for the iframe.
originBinaryBond host. Defaults to wherever sdk.js was loaded from.

The controller exposes room, inviteUrl, frame, on(type, fn), off(type, fn) and destroy().

Events

EventPayloadWhen
joined{ participants }The local user entered the call.
participants{ participants }Someone joined or left.
waiting{}The user is in the host's waiting room.
left{}The call ended for the local user.

Events carry counts only. Names, messages and media never leave the iframe.

Webhooks

Set an endpoint in the dashboard to receive room.created, room.ended, participant.joined and participant.left. Each request is a JSON POST:

{
  "id": "evt_9f2c…",
  "type": "room.ended",
  "created": 1760000000000,
  "data": { "room": "4be1c0a96f3d2e18", "ref": "meeting:42", "reason": "empty", "peakPeers": 3, "durationSec": 1820 }
}

data.room is a one-way reference: it identifies the room in your logs but can't be used to join. Verify every request using the X-BinaryBond-Signature header:

// Node.js
const [t, v1] = header.split(',').map(p => p.split('=')[1]);
const expected = crypto.createHmac('sha256', WEBHOOK_SECRET).update(`${t}.${rawBody}`).digest('hex');
const ok = crypto.timingSafeEqual(Buffer.from(v1), Buffer.from(expected))
  && Math.abs(Date.now() / 1000 - Number(t)) < 300;

Failed deliveries are retried three times with exponential backoff. Endpoints that resolve to private or loopback addresses are refused.

REST API

Authenticate with Authorization: Bearer <api key>. All bodies are JSON. A machine-readable OpenAPI 3.1 spec is available for code generators and API clients.

POST/v1/sessionsMint a session token (see above).
GET/v1/meWorkspace, plan limits and this month's usage.
PATCH/v1/meUpdate name, branding, webhook.url, domains.
POST/v1/me/rotate-keyIssue a new API key and revoke the current one.
GET/v1/usage?days=30Daily rooms, participant-seconds, joins and peak concurrency.
GET/v1/roomsLive rooms created with your tokens.
POST/v1/webhook/testSend a signed ping event to your endpoint.
POST/v1/billing/checkout{ plan } → Stripe Checkout URL (when billing is enabled).
POST/v1/billing/portalStripe customer portal URL.

Errors use HTTP status codes with { "error": "message" }. Requests are rate limited per IP; you'll receive 429 when over the limit.

Security model

  • Room key: 128 random bits generated in the browser, carried only in the URL fragment.
  • Derivation: HKDF-SHA-256 produces the public room ID, a membership token (server keeps only its SHA-256) and an AES-256-GCM key that never leaves the browser.
  • Signaling: SDP and ICE are sealed with AES-GCM, bound to sender and recipient as associated data, so the server can't read, forge or re-route them. That protects the DTLS fingerprints and prevents server-side man-in-the-middle.
  • Media & data: DTLS-SRTP and DTLS-SCTP, peer-to-peer (or through TURN, which only sees encrypted packets).
  • Verification: participants can compare safety numbers derived from both DTLS fingerprints.
  • Server storage: workspaces, hashed API keys and daily aggregate counters. No room IDs, IPs, names or content.
