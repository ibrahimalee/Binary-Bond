Quickstart

  1. Create a workspace in the dashboard and copy your API key. Keep it on your server.
  2. When a user opens a meeting in your app, request a session token from your backend.
  3. Pass the token to the browser and mount the call.
# Server: create a session token
curl -X POST https://YOUR_HOST/v1/sessions \
  -H "Authorization: Bearer $BINARYBOND_KEY" \
  -H "Content-Type: application/json" \
  -d '{"maxPeers": 4, "ttlSec": 900, "ref": "meeting:42"}'

# Response
{ "token": "v1.eyJ0aWQ...", "expiresAt": 1760000000000, "embedUrl": "https://YOUR_HOST/embed?token=..." }
<div id="call"></div>
<script src="https://YOUR_HOST/sdk.js"></script>
<script>
  const call = BinaryBond.mount('#call', { token: SESSION_TOKEN, height: '640px' });
  // Share call.inviteUrl with the other participants through your app.
  call.on('joined', (e) => console.log('participants', e.participants));
</script>

Add your site under Allowed embed origins in the dashboard. Browsers will refuse to show the call inside other sites.

Session tokens

A session token lets a browser create a meeting under your workspace. It applies your plan limits, counts usage against your quota and enables your branding. People joining an existing meeting only need its link.

FieldTypeDescription
ttlSecintegerToken lifetime, 30 seconds to 24 hours. Default 900.
maxPeersintegerMeeting capacity, from 2 up to your plan's limit.
maxMinutesintegerMeeting time limit, capped by your plan.
relaybooleanRoute all media through the relay so participants cannot see each other's IP address.
refstringYour own identifier, up to 64 characters of A-Z a-z 0-9 _ . : / -. Returned in webhooks and /v1/rooms.

Embed SDK

BinaryBond.mount(target, options) inserts the meeting in an iframe and returns a controller.

OptionDescription
tokenSession token from POST /v1/sessions.
roomAn existing meeting key to join. Leave it out to create a new meeting, then read call.room.
height, radius, titleIframe presentation.
originBinaryBond host. Defaults to the host that served sdk.js.

The controller has room, inviteUrl, frame, on(type, fn), off(type, fn) and destroy().

Webhooks

Set an endpoint in the dashboard to receive room.created, room.ended, participant.joined, participant.left and quota.warning as JSON POST requests.

{
  "id": "evt_9f2c...",
  "type": "room.ended",
  "created": 1760000000000,
  "data": { "room": "4be1c0a96f3d2e18", "ref": "meeting:42", "reason": "empty", "peakPeers": 3, "durationSec": 1820 }
}

Verify each request with the X-BinaryBond-Signature header and reject anything older than five minutes:

const [t, v1] = header.split(',').map((p) => p.split('=')[1]);
const expected = crypto.createHmac('sha256', WEBHOOK_SECRET).update(`${t}.${rawBody}`).digest('hex');
const valid = crypto.timingSafeEqual(Buffer.from(v1), Buffer.from(expected))
  && Math.abs(Date.now() / 1000 - Number(t)) < 300;

Failed deliveries are retried three times with backoff. Endpoints on private networks are refused.

REST API

Send Authorization: Bearer <api key> with every request. The full schema is in the OpenAPI spec.

POST/v1/sessionsCreate a session token.
GET/v1/meWorkspace, plan limits and this month's usage.
PATCH/v1/meUpdate name, branding, webhook URL and allowed origins.
POST/v1/me/rotate-keyIssue a new key and revoke the current one.
GET/v1/usageDaily meetings, participant time and peak size.
GET/v1/roomsMeetings currently running under your workspace.
POST/v1/webhook/testSend a signed test event.
POST/v1/billing/checkoutStart a plan upgrade through Stripe.

Limits and errors

Errors return a status code and { "error": "message" }. Requests are rate limited per IP address and return 429 when exceeded. When your monthly minutes run out, new meetings created with your tokens are refused until the next month or an upgrade.

Security model

  • The meeting key is 128 random bits created in the browser and carried only in the URL fragment.
  • HKDF-SHA-256 derives the public meeting ID, a membership token (the server stores only its hash) and an AES-256-GCM key that never leaves the browser.
  • Handshake messages are sealed with that key and bound to sender and recipient, so the server cannot read, alter or redirect them.
  • Media and data use DTLS-SRTP and DTLS-SCTP between devices, or through a TURN relay that only sees encrypted packets.
  • The server stores workspaces, hashed API keys and daily totals. It never stores meeting IDs, IP addresses, names or content.
